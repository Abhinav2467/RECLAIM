# Authoritative Revenue Truth & Mathematics

> **RECLAIM Revenue Truth Engine**: Establishing Immutable Monetary Provenance Before Action

---

## 1. Overview

A fundamental engineering principle of RECLAIM is that **an AI decision agent must never directly infer, hallucinate, or fabricate financial values**. Monetary values must originate from an authoritative read model backed by gateway settlement data ([`apps/api/app/domain/revenue_truth.py`](../apps/api/app/domain/revenue_truth.py)).

---

## 2. Authoritative Revenue Mathematics

RECLAIM maintains three distinct monetary attributes for every order and payment:

### **1. Expected Amount ($A_{\text{expected}}$)**
The total gross transaction intent recorded at order creation in the merchant's checkout system (`orders.amount_total`).

### **2. Captured Amount ($A_{\text{captured}}$)**
The total sum of authoritatively settled gateway funds confirmed by signed provider webhook payloads (`payments.amount` where `payment_state = 'captured'`).

### **3. Recoverable Amount ($A_{\text{recoverable}}$)**
The actual monetary exposure remaining at risk:

$$A_{\text{recoverable}} = A_{\text{expected}} - A_{\text{captured}}$$

### **4. Current At-Risk Exposure**
* While a case is in `VERIFYING`, `EXECUTING`, or `DIAGNOSED` status, the entire recoverable amount remains exposed:
  $$\text{Current Exposure} = A_{\text{recoverable}}$$
* When gateway reconciliation confirms payment settlement (`status = RECOVERED`), the current risk exposure transitions to:
  $$\text{Current Exposure} = \$0.00$$

## 3. Monetary Aggregate Definitions

The merchant operational overview read model ([`apps/api/app/api/overview.py`](../apps/api/app/api/overview.py)) computes portfolio-wide aggregates across all merchant cases:

| Portfolio Aggregate | Mathematical Definition | Operational Meaning |
| :--- | :--- | :--- |
| **Revenue at Risk** | $\sum A_{\text{recoverable}} \quad \forall \text{ active cases in } \{\text{VERIFYING}, \text{DETECTED}, \text{DIAGNOSED}\}$ | Total monetary capital currently exposed to potential loss across active cases. |
| **Expected Net Recovery** | $\sum \text{Expected Net Recovery}(a^*) \quad \forall \text{ active cases}$ | Probabilistic net recovery expected after subtracting intervention friction costs. |
| **Verified Recovered** | $\sum A_{\text{recoverable}} \quad \forall \text{ cases where } \text{status} = \text{'RECOVERED'}$ | Cumulative financial capital authoritatively confirmed captured by gateway settlement. |
| **Capital Preserved** | $\sum A_{\text{recoverable}} \quad \forall \text{ cases where } \text{status} = \text{'NO\_ACTION'}$ | Merchant capital preserved by intentionally halting unviable intervention expenditure. |

## 4. Payment Provenance & Metadata

Every payment record maintains complete provider provenance ([`apps/api/app/db/models.py`](../apps/api/app/db/models.py)):

* `provider_payment_id`: External payment ID issued by Razorpay (e.g. `pay_demo_testrun1`).
* `provider_event_id`: Unique webhook notification event identifier (e.g. `evt_demo_testrun1`).
* `provider_state`: Gateway settlement state (`created`, `authorized`, `captured`, `failed`).
* `provider_state_at`: Authoritative UTC timestamp generated by the provider gateway.
* `provider_failure_code`: Standardized gateway error code (e.g. `BAD_REQUEST_ERROR`, `GATEWAY_TIMEOUT`).

---

## 5. Stale, Duplicate, & Out-of-Order Handling

1. **Duplicate Webhook Prevention**: The database enforces a unique constraint on `(merchant_id, provider_event_id)`. Duplicate webhook deliveries are acknowledged with HTTP 200 and ignored.
2. **Out-of-Order Event Sequencing**: Incoming events are compared against `provider_state_at`. If a received event has an older timestamp than the current `provider_state_at`, it is recorded in `raw_webhook_events` for auditability but ignored by state reconciliation.
3. **Stale Context Guard**: When evaluating a decision, the policy engine checks that `context_version` matches the case version. If a new payment event arrives during evaluation, the context version increments and the stale decision is safely rejected.
